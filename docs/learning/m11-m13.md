# Studying Kairo M11–M13

This extends the preserved M0–M3, M3–M6 and M7–M10 guides. It documents what was
implemented and observed; it does not mark the developer's study as complete.
Work sequentially, reading contracts and failure tests before following call chains.

## M11 — A control plane you can inspect

The frontend is a projection of backend state, not a second scheduler. Read
`apps/web/src/lib/api.ts`, then `apps/web/src/app/page.tsx`. Types describe records;
fetch errors retain an explicit stale-data warning. Aggregate cards come from SQL
counts, not hardcoded examples. Polling refreshes collections; SSE adds ordered run
events. React state handles selection/loading/errors while PostgreSQL owns truth.
`apps/web/src/app/globals.css` defines the dark visual system and responsive layouts.
No external imagery/fonts or fabricated metrics are needed for an engineering console.

Read `apps/api/src/kairo_api/dashboard.py`. Task submission atomically creates actual
queued work. Tasks currently have one run per submission. The overview counts all
runs while collections paginate. Agent arena cards point to actual child run IDs and
dependencies; evaluation charts show stored scenario results, distinct from task
success. Comparing changed environments/source/budgets is rejected by the existing
comparison contract. Completed evaluations may contain failures.

SSE is a unidirectional HTTP stream. Each event has a durable sequence ID. On reconnect,
Last-Event-ID requests later records; the client also deduplicates by sequence and
bounds its rendered timeline to 1,000 events. The full paginated API history remains
available. Worker crashes do not erase past events. This initial implementation polls
the database; it does not need a broker or bidirectional WebSocket protocol.

### Approval is a backend capability

Read `packages/core/src/kairo_core/approvals.py` and migration
`migrations/versions/0006_approvals.py`, then the authorization hook in `runtime.py`
and wiring in `orchestration/worker.py`. The model asks for an action; its request
never grants authority. The backend pins canonical action inputs, invocation, run,
attempt and current lease. Consumption is once-only. Permission/argv validation still
happens after approval; an approved request cannot gain network access or escape its
workspace. Approval denial performs no operation. Expired/cancelled/stale requests
are audit records, not actionable requests. A crash before dispatch may prompt again.

The run moves RUNNING → WAITING_FOR_APPROVAL → RUNNING → WAITING_FOR_TOOL. Terminal
states remain immutable. User waiting consumes the run budget, so a forgotten approval
cannot hold a lease forever. `tests/persistence/test_dashboard.py` performs actual
write/no-write assertions, decision replay rejection, cancellation and SSE cursor replay
against PostgreSQL and real workers. Frontend Playwright tests use the real API rather
than intercepting responses. Scripted model decisions are clearly labelled no-inference.

### Local setup and review

```sh
cd /Users/somyadeeptarat/Desktop/Kairo
uv sync --locked
export KAIRO_DATABASE_URL='postgresql+psycopg://kairo:kairo_local_only@127.0.0.1:55432/kairo'
docker compose -p kairo-m3 -f infrastructure/compose/compose.yaml up -d --wait
uv run --locked alembic upgrade head
uv run --locked python scripts/serve.py
# In another terminal:
npm --prefix apps/web ci
npm --prefix apps/web run dev
```

Open http://127.0.0.1:3000. Submit a scripted infrastructure example, inspect the
WAITING_FOR_APPROVAL event, approve exactly its write, and verify tool evidence and
checkpoints after completion. Then deny a different action and check that no file
appeared. Select Ollama only when its server and chosen installed model are available;
there is no model download hidden in task execution.

Think through: why does disabling a button not enforce authorization? Why can a
reconnecting stream repeat delivery without repeating a tool? Why are a request's
status and its current actionability different? What happens if a decision arrives
after a lease expires? ADR 0015 records alternatives and scaling limits.
