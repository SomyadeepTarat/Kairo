# Studying Kairo M11–M13

This extends the preserved M0–M3, M3–M6 and M7–M10 guides. It documents what was
implemented and observed; it does not mark the developer's study as complete.
Work sequentially, reading contracts and failure tests before following call chains.

## M11 — A control plane you can inspect

The frontend is a projection of backend state, not a second scheduler. Read
`apps/web/src/lib/api.ts`, then `apps/web/src/app/page.tsx`. Types describe records;
fetch errors retain an explicit stale-data warning. Aggregate cards come from SQL
counts, not hardcoded examples. Polling refreshes collections; SSE adds ordered run
events. React state handles selection/loading/errors while PostgreSQL owns truth.
`apps/web/src/app/globals.css` defines the dark visual system and responsive layouts.
No external imagery/fonts or fabricated metrics are needed for an engineering console.

Read `apps/api/src/kairo_api/dashboard.py`. Task submission atomically creates actual
queued work. Tasks currently have one run per submission. The overview counts all
runs while collections paginate. Agent arena cards point to actual child run IDs and
dependencies; evaluation charts show stored scenario results, distinct from task
success. Comparing changed environments/source/budgets is rejected by the existing
comparison contract. Completed evaluations may contain failures.

SSE is a unidirectional HTTP stream. Each event has a durable sequence ID. On reconnect,
Last-Event-ID requests later records; the client also deduplicates by sequence and
bounds its rendered timeline to 1,000 events. The full paginated API history remains
available. Worker crashes do not erase past events. This initial implementation polls
the database; it does not need a broker or bidirectional WebSocket protocol.

### Approval is a backend capability

Read `packages/core/src/kairo_core/approvals.py` and migration
`migrations/versions/0006_approvals.py`, then the authorization hook in `runtime.py`
and wiring in `orchestration/worker.py`. The model asks for an action; its request
never grants authority. The backend pins canonical action inputs, invocation, run,
attempt and current lease. Consumption is once-only. Permission/argv validation still
happens after approval; an approved request cannot gain network access or escape its
workspace. Approval denial performs no operation. Expired/cancelled/stale requests
are audit records, not actionable requests. A crash before dispatch may prompt again.

The run moves RUNNING → WAITING_FOR_APPROVAL → RUNNING → WAITING_FOR_TOOL. Terminal
states remain immutable. User waiting consumes the run budget, so a forgotten approval
cannot hold a lease forever. `tests/persistence/test_dashboard.py` performs actual
write/no-write assertions, decision replay rejection, cancellation and SSE cursor replay
against PostgreSQL and real workers. Frontend Playwright tests use the real API rather
than intercepting responses. Scripted model decisions are clearly labelled no-inference.

## M12 — From model text to a verified repair

Read `examples/coding-agent/reference_app/calculator.py` and
`examples/coding-agent/reference_app/test_calculator.py`. The calculator is a real
CLI/module with a deliberate discount bug. The tests encode behavioral expectations,
including zero/full/invalid discounts. They remain unchanged. This is small enough
for a local model to inspect, but still exercises actual files, Python tests and Git.

Read `packages/core/src/kairo_core/coding_demo.py`. `demo_spec()` supplies task
instructions, known fixture files and exact command grants, not a hidden fixed answer
in live mode. Scripted mode explicitly supplies the repair and is used only for
infrastructure testing. `run_demo()` judges actual baseline/final command results,
unchanged acceptance tests and a real diff, independently of final model text.

`orchestration/worker.py` prepares caller fixtures before the first RUNNING transition.
Preparation may repeat idempotently before execution; recovery after execution does
not reseed. Git init/baseline commit happen in the isolated task workspace with fixed
bootstrap argv. The host repository and global Git config are untouched. Fixture
limits/protected paths are validated in `orchestration/spec.py`.

The approval gate remains active. Without `--approve-demo-actions`, use the dashboard
to approve each requested exact action. With that explicit flag, a narrow operator
policy approves calculator.py writes and the fixed test argv only. It rejects test
changes, arbitrary commands, network and agent-created commits. This supports an
unattended reproducible demonstration without claiming a human reviewed every action.

### Fault boundaries and uncertainty

The driver launches one targeted worker process, waits for a durable tool result,
kills that process with SIGKILL, expires only its lease with database time, reaps and
launches its replacement. Production recovery reconstructs context and avoids replay
of confirmed work. Attempt IDs/events show the actual interruption. This requires no
competing consumers for that task; run the API in inspection-only mode during the demo.

The first driver attempt killed during a newly approved command. The runtime correctly
blocked its uncertain outcome rather than guessing. The refined safe-resume experiment
stops granting new actions and waits until no dispatched mutation is unresolved before
killing. This is a controlled failure boundary, not a claim that arbitrary interruptions
are always safe. Existing M6 uncertainty/reconciliation tests remain authoritative.

```sh
# Keep API inspection available, with the driver's own worker controlling the demo:
KAIRO_EMBEDDED_WORKER=0 uv run --locked python scripts/serve.py
# Another terminal, same database URL; Ollama running with an installed model:
uv run --locked python scripts/demo_coding.py --model qwen3:4b
# Or explicitly authorize the narrow isolated-demo policy:
uv run --locked python scripts/demo_coding.py --approve-demo-actions
# Deterministic infrastructure validation, clearly labelled:
uv run --locked python scripts/demo_coding.py --scripted --approve-demo-actions
```

Reports and workspaces live under ignored `.kairo/`; a selected measured report is
preserved in `docs/demo/`. Inspect the printed run UUID in the dashboard. Verify the
baseline failure, checkpoint/attempt change, approval decisions, actual patch, unchanged
tests and independent final oracle. Ask why a completed tool with exit code 1 can be
useful evidence, why test edits cannot establish correctness, and why checkpoint
recovery must not reset the workspace to its initial files. See ADR 0016.

### What the live failures taught us

A free-form local model recovered and explained the error but did not change the
file. The oracle rejected it. A clearer prompt alone still did not establish reliable
progress. Those runs remain failure evidence, not successful autonomy metrics.

The reference application now uses `packages/core/src/kairo_core/coding_model.py`.
The harness selects read/test/diff operations, and Ollama generates the proposal,
complete replacement source, and final review. Three bounded repair rounds are
possible; final review is requested only after recorded tests pass. The report calls
this **application-orchestrated live Ollama**, not unrestricted autonomous behavior.
Its replacement code is actually generated by the model. Scripted mode remains a
separate branch with a prescribed patch for deterministic infrastructure tests.

The first staged patch produced invalid nested arguments JSON when multiline code
required a second layer of escaping. Read `ProviderTool` in `ollama.py`: the provider
now generates a normal arguments object. The adapter serializes it once into the
existing kernel ToolRequest string contract. This separates provider representation
from internal persistence and removes a fragile burden from the model. The multiline
source regression in `tests/core/test_ollama.py` verifies quotes/newlines roundtrip.

Explain why choosing deterministic inspection/testing operations does not fabricate
model-generated code, why this narrower claim matters, and why a terminal COMPLETED
state is a runtime outcome rather than proof of the application's acceptance criteria.

## M13 — Release engineering is another test boundary

A release is more than a successful development checkout. Its dependency locks,
versioned migrations, frontend sources, fixture data and setup commands must work
from a fresh source snapshot without relying on ignored local state. Read
`MANIFEST.in`, `pyproject.toml`, `apps/web/package-lock.json`, `docs/installation.md`
and `docs/milestones/M13.md`. The source archive includes runtime infrastructure,
web app, examples, benchmarks and docs. The wheel packages importable Python modules;
source-checkout CLI commands are not advertised as a standalone wheel installer.

Version 0.1.0 identifies this local engineering release. The developer explicitly
chose to keep the project unlicensed, so no LICENSE or external distribution/push
was performed. That decision is recorded in ADR 0004 and overrides the PRD's planned
open-source distribution. Do not invent release tags, hosted URLs or permissions.

`scripts/check.py` optionally includes frontend typing/format/production build when
KAIRO_CHECK_WEB=1; failure propagates. Its unit regression verifies that a frontend
failure cannot become a green gate. Playwright tests separately drive real API/worker
execution. Backend tests create/drop isolated database schemas. Live model examples
remain separate from deterministic checks. A fresh-checkout smoke test exercises actual
submission, approval and completion, not just dependency installation or CLI presence.

Read `docs/security.md`. Release review adds Host checks and mutation Origin checks,
but there is still no public authentication or multi-user isolation. Seed file names
are rejected before claiming work when malformed/protected. Security documentation
states the boundaries that tests demonstrate and the guarantees the system does not
provide. A passing finite suite cannot prove absence of vulnerabilities.

Generated `docs/api/openapi.json` comes from the actual API factory. It cannot promise
unimplemented routes. `apps/web/scripts/record-demo.mjs` records an inspection of the
persisted real run; it does not synthesize model interactions or relabel an inspection
as a real-time capture. Raw records provide the underlying execution evidence.

Release metrics must be defensible: deterministic tests passed, no skips only when
services were enabled, actual worker termination/recovery, an actual independent test
result, and measured tool/model observations. Avoid invented coverage, throughput,
latency advantages, general autonomous coding success or claims of personal mastery.
The release report lists small-sample, model and local-environment limitations.

Before describing this project in an interview, trace one concrete claim back to
its test/report. Explain why an installed CLI is not a healthy service, why fresh
installation differs from an editable checkout, and why preserved failures strengthen
an engineering account. See ADR 0017 for release alternatives and assumptions.

### Fresh-install findings

The fresh environment initially needed locked Python wheels that were not in the
selected cache; an offline cache miss is not proof that installation is broken.
The documented online initial install downloaded the free locked packages, then
all commands used the new environment. A clean npm install/build also succeeded.
No ignored source environment or node_modules was copied into the snapshot.

The first fresh test invocation accidentally inherited the embedded-worker launch
flag. An API test then started an extra background worker, violating its explicit
worker-count contract. `tests/conftest.py` now clears that inherited flag: tests own
their worker processes unless explicitly opting in. The corrected snapshot reran all
255 Python tests without skips and three real browser tests. The smoke task verified
an actual fresh-workspace file, one approval, two tools and SSE replay. Its separate
database schema was dropped after validation. This is installation/environment
validation, not a claim that a remote user has independently reviewed the project.


The final browser regression also verifies that direct evaluation runs do not offer
queue cancellation they cannot support. Queue-backed executions retain cancellation;
direct runs remain under their evaluation driver's control. The final fresh-source
browser suite contains three real API tests. Release review fixed this misleading
control rather than shipping a button that would only return a not-found error.
