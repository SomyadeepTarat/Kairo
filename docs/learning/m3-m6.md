## M3: What durable execution history gives us

The central M3 idea is to save progress while work happens. Saving only RunResult
at completion loses the runs that crash midway. `packages/core/src/kairo_core/events.py`
defines an awaited Recorder port; `packages/core/src/kairo_core/persistence/repository.py`
implements it using PostgreSQL. Read `start`, then `record`.

A task describes work, a run describes its lifecycle, and an attempt identifies an
execution incarnation. Events record ordered history. Tool records distinguish
requested/started calls from known completion. Current status is a snapshot for
inspection; it must agree with the event that changed it. Each append locks its run,
updates the snapshot and inserts a per-run sequence-numbered event in one transaction.
If insertion fails, both state and sequence roll back. A timestamp alone is not order.

The runtime commits a request/dispatch before invoking external work, then records
its outcome. This makes uncertainty visible after crashes. The database and a file
write do not share a transaction: a write can succeed just before its acknowledgment
is lost. Recovery must preserve that distinction instead of assuming an exception
means nothing happened. M3 inspection alone cannot resume or safely retry work.

Read `migrations/versions/0001_execution_history.py`, then
`tests/persistence/test_repository.py` and `tests/persistence/test_interruption.py`.
The tests use real PostgreSQL schemas, including a trigger-induced event failure
and a killed execution process. FastAPI at `apps/api/src/kairo_api/main.py` reads
these records independently of the executing process. SQLAlchemy maps data and
manages sessions; it does not make external actions transactional.

Checkpoint for understanding: explain the difference between durable history,
a checkpoint, and a recoverable side effect. Sketch the write-succeeded/acknowledgment-
lost window and say what the database can actually prove.

## M4: The workspace and container boundary

A Python path check cannot isolate an arbitrary command. A command can call other
programs, inspect environment variables, open paths and create child processes.
`packages/core/src/kairo_core/execution/sandbox.py` therefore executes commands in
containers. `Workspaces` creates new directories named by UUID under a developer-
controlled root; it never silently reuses an existing directory for a new identity.
The worker must use only its assigned managed workspace.

Read `DockerExecutor.create_arguments` before `execute`. Fixed Docker flags come
before the trusted image name; the approved command argv comes afterward as the
container command. No model text is parsed as Docker flags. The image is built
explicitly from `infrastructure/docker/Dockerfile.sandbox`, never pulled implicitly
while running a task. Docker commands use subprocess argv, not host shell evaluation.

Only /workspace is a host mount. The container root is read-only; /tmp is a bounded
temporary filesystem. Network is none, capabilities are dropped, privilege gain is
prohibited, and the process runs as the local nonroot UID so it can write the owned
workspace on macOS bind mounts. No host secret environment or Docker socket is
forwarded. CPU, memory, process count and file size limits narrow resource failures.
They do not provide an aggregate disk quota or defend against every kernel escape.

Permission and approval are different: `command.execute` enables the tool boundary,
but the executor still requires the exact argv in its approved_commands set.
Another command or another workspace is denied before container creation. This is
a real backend check; it is not a substitute for a future interactive approval UI.
Approvals do not make a command harmless, so the isolation controls remain necessary.

Container execution has a lifecycle: create, attach/start, inspect exit status,
remove in finally. stdout/stderr are drained concurrently and bounded so a verbose
process cannot accumulate unlimited output. On timeout or cancellation, the host
attachment process is reaped and the container is forcibly removed. A nonzero
command exit is recorded as a real return code, not replaced with success text.
Execution labels let a supervisor find containers after the owning worker dies.
If Docker is unavailable, cleanup cannot be assumed; the error must remain visible.

File tools in `packages/core/src/kairo_core/tools/files.py` still reject traversal,
symlinks, hardlinks, protected paths and oversized/nonregular files. Containers
protect arbitrary commands; descriptor-relative file access protects exposed host
file tools. Neither replaces the other. Read `tests/execution/test_sandbox.py` to
see real assertions for host environment, network, root writes and cleanup, plus
pure tests for exact approval and generated resource arguments.

Build and test from the repository root:

```sh
docker build -t kairo-sandbox:local -f infrastructure/docker/Dockerfile.sandbox .
export KAIRO_TEST_DOCKER=1
uv run --locked pytest tests/execution --require-docker -q
```

Checkpoint for understanding: what does killing `docker start --attach` fail to
prove about the container process? Why must cleanup use the container name/label?
Why does a readonly root still allow writing /workspace, and why must host secrets
never be mounted even when a command was approved?

## M5: A queue is an ownership protocol, not just a list

Read `packages/core/src/kairo_core/orchestration/spec.py`, then queue.py and worker.py
in that directory. Migration `migrations/versions/0002_queue_workers.py` adds jobs
and workers. A submission atomically creates its execution identities and QUEUED
history together with a typed JobSpec. Scripts are explicit deterministic model
inputs, not a hidden mock presented as inference. A replaceable model factory lets
the worker remain independent of the provider transport.

Claiming uses SELECT FOR UPDATE SKIP LOCKED. Two transactions cannot own the same
row, and a second consumer can skip a temporarily locked row instead of waiting.
The claim transaction commits quickly; it does not remain open for the whole agent
run. A worker-row lock plus a count of its active claims enforces configured capacity.
Multiple local processes can claim distinct jobs. Ordering among available rows is
best effort, not strict FIFO under contention. PostgreSQL is already our durable
store, so adding Redis here would create another system to keep consistent.

A claim has a random lease token and a database-time expiry. The worker heartbeats
while the kernel runs. LeaseRecorder locks/checks the job and writes the execution
event in the same transaction; checking first and later saving through another
transaction would leave a race where a stale owner could write after takeover.
Queued runs cannot use the unfenced M3 recorder. RunBinding lets the kernel execute
the already-created run instead of inventing a second execution identity.

A lease only describes authority; it cannot stop an old process. The worker also
holds a Unix flock outside the agent mount for the lifetime of the execution.
A reaper fences expired claims as REAPING, stops containers bearing the old token,
and requires the same workspace lock before finalizing. A killed process releases
its file descriptors automatically. An alive but frozen process can keep the lock,
so reclamation waits rather than allowing concurrent writers. This design assumes
all workers run on one host and share the same workspace root; it is not a general
distributed filesystem fencing solution.

Cancellation is durable intent. A queued job can become CANCELLED immediately;
a running job's heartbeat communicates the request to the kernel, which joins tool
cleanup before recording cancellation. The 202 HTTP response says accepted, not
stopped. GET queue/worker routes report stored state, capacity and measured heartbeat
times; they do not invent an alive animation. The loop has bounded slots and a
separate reaper. Service polling continues until stopped; individual work is bounded.

Run the service from the root after migrating:

```sh
uv run --locked alembic upgrade head
uv run --locked python scripts/enqueue.py /absolute/path/to/job.json
uv run --locked python scripts/worker.py --capacity 2 --root .kairo/workspaces
```

A minimal job file is `{"task":"script demo","steps":[{"kind":"final","text":"done"}]}`.
For commands, approved_commands is a list of exact argv lists supplied explicitly
by the caller. Workers never infer approval from model output. The root is local
managed state, ignored by Git. `--once` performs one claim/execution attempt.

Read `tests/persistence/test_queue.py`: competing transactions, capacity, stale
leases, bypass rejection, queued and active cancellation, workspace lock exclusion,
multiple workers and a real approved container command are all separate concerns.
M5's abandonment policy fails the run; it does not guess how to retry. That safe
baseline is extended only by M6's recovery protocol.

Checkpoint for understanding: why are the DB token, container label and filesystem
lock all needed? What if an old worker wakes after expiry? What if Docker cannot
confirm cleanup? Explain why neither a heartbeat nor a lock alone is sufficient.

## M6: Recovering progress without repeating unsafe work

Start at `packages/core/src/kairo_core/checkpoints.py`, then follow snapshot,
checkpoint and resume in `packages/core/src/kairo_core/runtime.py`. KernelSnapshot
is a versioned, validated continuation: immutable messages, next logical step,
remaining time, and optionally a known final response. Unsupported versions,
malformed message roles, invalid counters and nonfinite/negative budgets are rejected.
A RunResult returned by a resumed attempt contains that attempt's new steps; the
database retains all earlier attempts and events.

A checkpoint is not a filesystem backup. `CheckpointRow` in
`packages/core/src/kairo_core/persistence/tables.py` retains state, event sequence,
attempt and a workspace identity reference. The files remain in the managed local
directory. Recovery assumes no external modifications. Missing workspace data blocks
rather than silently restarting in an empty folder. Presence is checked again at
claim time, so deletion during retry backoff cannot cause an empty recreation. A
claimant that died before the run ever started may still allocate its first directory;
that is different from losing an existing execution workspace. There is no automatic filesystem
rollback or aggregate workspace quota.

Normal safe boundaries are initial RUNNING, a completed Continue step, and a known
tool result supplied to the next context. After a tool, context checkpoint and
RUNNING transition share one database transaction. A known final output is also
retained before terminal finalization. This does not remove every crash window;
we must still reason about records that committed just before a crash.

### The gap that makes naive replay unsafe

Suppose the tool appends `x` to a file. The tool_finished record commits, then the
worker dies before saving the next checkpoint. Restarting only from the checkpoint
would append another `x`. The database already proves the first call finished, so
repeating it would be our orchestration bug.

Read `project` in `packages/core/src/kairo_core/orchestration/recovery.py`. Starting
from the latest checkpoint, it examines later committed events. A later model
request records the exact context and logical step; a known Continue adds its
assistant text; a known tool result becomes the same assistant/tool message pair
used by the live runtime. A known Final can be finalized without inference. Projection
runs no model, command or file tool. It reconstructs what is proven, rather than
executing history again.

If tool_started exists but tool_finished does not, a mutation's outcome is uncertain.
The tool may have completed and lost acknowledgment, or may never have reached its
side effect. Only read-only work can be safely requested again automatically.
Retries cannot turn an unknown outcome into known failure.

### Recovery is an ownership and state transition protocol

Read `recover` after `project`. The worker reaper has already fenced the old token,
stopped its containers and acquired the workspace lock. The recovery transaction
locks the job/run, checks cancellation and uncertainty, validates the workspace and
checkpoint, and derives safe continuation. It then ends the old attempt with
LEASE_EXPIRED and creates a new attempt, atomically setting current_attempt_id and
QUEUED with an attempt_recovered event. The ordinary state graph is unchanged;
the new attempt explicitly versions this nonterminal lifecycle reset. A terminal
COMPLETED, FAILED or CANCELLED run is not resumed.

| Observed condition | Implemented action |
| --- | --- |
| Old owner still holds the local workspace lock | Keep REAPING; do not dispatch a second owner |
| Confirmed completed tool, even after the last checkpoint | Consume its result; do not call it again |
| No response to a model request, or unfinished read-only call | Retry that logical step within the attempt/time budgets |
| Unknown mutation in an interrupted nonterminal run | BLOCKED / UNCERTAIN_TOOL; await operator intervention |
| Already terminal failed run, including a known partial mutating failure | Keep FAILED and its uncertain tool record; inspect effects before starting separate work |
| Missing workspace | BLOCKED / WORKSPACE_MISSING |
| Redacted checkpoint/context | BLOCKED / REDACTED_CONTEXT; never execute altered input |
| Invalid or unsupported recorded context | BLOCKED with an inspectable reason |
| Attempt or original run deadline exhausted | Terminal FAILED; no more work |
| Cancellation requested | Cancel after cleanup; preserve history/uncertainty |

JobSpec.max_attempts defaults to three and allows one through ten. A claim consumes
an attempt even if its process dies early. Backoff doubles from one second up to
30 seconds. Logical step numbering and the original step limit are preserved.
Unknown model/read requests can mean more physical calls than logical completed
steps, but physical attempts are bounded separately. The original run budget begins
at its first RUNNING timestamp; downtime and backoff consume it. Recovered workers
recompute remaining time rather than receiving another full budget.

### Explicit reconciliation is a claim requiring evidence

Inspect the blocked queue status, events and exact tool invocation. If you cannot
prove the outcome, leave it blocked or cancel it. Do not assume that a timeout or
nonzero command exit means no files were changed. There is no automatic retry for
uncertain mutations.

`Queue.reconcile` in `packages/core/src/kairo_core/orchestration/queue.py` accepts a
reason and exactly one resolution: proven nonexecution, or a known tool result.
Completed output must validate against that tool's output schema. Run, attempt and
invocation identities must match the blocked action; a different ID or terminal run
is rejected. The decision is recorded as tool_reconciled and sent through reaping/
ownership checks again. This is local operator intervention, not proof that the
backend has independently observed the asserted fact.

Use the explicit CLI only after investigating that specific action:

```sh
uv run --locked python scripts/reconcile.py RUN_UUID TOOL_UUID \
  --not-executed --reason 'Evidence that this invocation never reached its side effect'
```

Or supply `--completed-output` with the tool's actual JSON result and a reason.
For a known command result, the schema includes stdout, stderr and returncode; a
known nonzero exit can still have a confirmed result and partial effects. The
recovery projector consumes that outcome without rerunning the command. The API
also provides `POST /api/v1/runs/{run_id}/reconcile`. It is trusted-local and not
accessible from network-disabled task containers.

Start the API separately using the README command. Current inspection/control paths:

- `GET /api/v1/runs`, run detail, ordered events and tool records.
- `GET /api/v1/runs/{run_id}/queue`, including attempts, availability and blocking reason.
- `GET /api/v1/runs/{run_id}/checkpoints`, paginated by event sequence.
- `GET /api/v1/workers` and worker detail, including capacity/heartbeat/active claims.
- `POST /api/v1/runs/{run_id}/cancel`, which acknowledges intent.
- `POST /api/v1/runs/{run_id}/reconcile`, which validates an explicit operator decision.

There are no placeholder model-provider, dashboard or approval controls. Submission
currently uses the typed scripted-job CLI and the worker's replaceable Model factory.
The scripted example really executes its approved command and reads the result;
it does not claim live LLM reasoning.

### Read the failure tests as executable engineering arguments

Run with actual services rather than counting skips:

```sh
export KAIRO_TEST_DATABASE_URL="$KAIRO_DATABASE_URL"
export KAIRO_TEST_DOCKER=1
uv run --locked python scripts/check.py
uv run --locked pytest tests/persistence/test_recovery.py --require-postgres --require-docker -q
```

`tests/persistence/test_recovery.py` kills real worker processes at controlled
boundaries and inspects real PostgreSQL/container/filesystem state. It verifies an
append remains exactly one `x` after recovery, both after checkpointing and in the
committed-result/checkpoint gap. It blocks an unknown dispatch, validates explicit
reconciliation, consumes a proven result without reexecution, and finalizes a
recorded final answer without another model call. Other cases exercise attempt/
deadline limits, malformed/redacted/missing state and a lock retained by an old owner.
The controlled interceptors are test instrumentation, not fake product behavior.

One negative test found that later event projection could overwrite a redaction
marker before validation. Recovery now rejects redacted checkpoints before
projection as well as checking the projected state. That is a deliberately
conservative limitation rather than silently supplying altered context.

## What remains after M6

This is a local trusted-developer runtime, not adversarial multi-tenant isolation.
It does not claim exactly-once external effects, distributed-host filesystem
fencing, recovery from lost/externally edited workspace data, complete secret
detection, or a live-model quality benchmark. Containers share a kernel; a daemon
outage can delay cleanup and therefore recovery. Context/history size optimization
is M7, multi-agent coordination M8, expanded tracing M9, evaluations M10, and the
frontend M11. None of those later milestones is implemented by this work.
