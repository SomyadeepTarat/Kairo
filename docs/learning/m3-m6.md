## M3: What durable execution history gives us

The central M3 idea is to save progress while work happens. Saving only RunResult
at completion loses the runs that crash midway. `packages/core/src/kairo_core/events.py`
defines an awaited Recorder port; `packages/core/src/kairo_core/persistence/repository.py`
implements it using PostgreSQL. Read `start`, then `record`.

A task describes work, a run describes its lifecycle, and an attempt identifies an
execution incarnation. Events record ordered history. Tool records distinguish
requested/started calls from known completion. Current status is a snapshot for
inspection; it must agree with the event that changed it. Each append locks its run,
updates the snapshot and inserts a per-run sequence-numbered event in one transaction.
If insertion fails, both state and sequence roll back. A timestamp alone is not order.

The runtime commits a request/dispatch before invoking external work, then records
its outcome. This makes uncertainty visible after crashes. The database and a file
write do not share a transaction: a write can succeed just before its acknowledgment
is lost. Recovery must preserve that distinction instead of assuming an exception
means nothing happened. M3 inspection alone cannot resume or safely retry work.

Read `migrations/versions/0001_execution_history.py`, then
`tests/persistence/test_repository.py` and `tests/persistence/test_interruption.py`.
The tests use real PostgreSQL schemas, including a trigger-induced event failure
and a killed execution process. FastAPI at `apps/api/src/kairo_api/main.py` reads
these records independently of the executing process. SQLAlchemy maps data and
manages sessions; it does not make external actions transactional.

Checkpoint for understanding: explain the difference between durable history,
a checkpoint, and a recoverable side effect. Sketch the write-succeeded/acknowledgment-
lost window and say what the database can actually prove.

## M4: The workspace and container boundary

A Python path check cannot isolate an arbitrary command. A command can call other
programs, inspect environment variables, open paths and create child processes.
`packages/core/src/kairo_core/execution/sandbox.py` therefore executes commands in
containers. `Workspaces` creates new directories named by UUID under a developer-
controlled root; it never silently reuses an existing directory for a new identity.
The worker must use only its assigned managed workspace.

Read `DockerExecutor.create_arguments` before `execute`. Fixed Docker flags come
before the trusted image name; the approved command argv comes afterward as the
container command. No model text is parsed as Docker flags. The image is built
explicitly from `infrastructure/docker/Dockerfile.sandbox`, never pulled implicitly
while running a task. Docker commands use subprocess argv, not host shell evaluation.

Only /workspace is a host mount. The container root is read-only; /tmp is a bounded
temporary filesystem. Network is none, capabilities are dropped, privilege gain is
prohibited, and the process runs as the local nonroot UID so it can write the owned
workspace on macOS bind mounts. No host secret environment or Docker socket is
forwarded. CPU, memory, process count and file size limits narrow resource failures.
They do not provide an aggregate disk quota or defend against every kernel escape.

Permission and approval are different: `command.execute` enables the tool boundary,
but the executor still requires the exact argv in its approved_commands set.
Another command or another workspace is denied before container creation. This is
a real backend check; it is not a substitute for a future interactive approval UI.
Approvals do not make a command harmless, so the isolation controls remain necessary.

Container execution has a lifecycle: create, attach/start, inspect exit status,
remove in finally. stdout/stderr are drained concurrently and bounded so a verbose
process cannot accumulate unlimited output. On timeout or cancellation, the host
attachment process is reaped and the container is forcibly removed. A nonzero
command exit is recorded as a real return code, not replaced with success text.
Execution labels let a supervisor find containers after the owning worker dies.
If Docker is unavailable, cleanup cannot be assumed; the error must remain visible.

File tools in `packages/core/src/kairo_core/tools/files.py` still reject traversal,
symlinks, hardlinks, protected paths and oversized/nonregular files. Containers
protect arbitrary commands; descriptor-relative file access protects exposed host
file tools. Neither replaces the other. Read `tests/execution/test_sandbox.py` to
see real assertions for host environment, network, root writes and cleanup, plus
pure tests for exact approval and generated resource arguments.

Build and test from the repository root:

```sh
docker build -t kairo-sandbox:local -f infrastructure/docker/Dockerfile.sandbox .
export KAIRO_TEST_DOCKER=1
uv run --locked pytest tests/execution --require-docker -q
```

Checkpoint for understanding: what does killing `docker start --attach` fail to
prove about the container process? Why must cleanup use the container name/label?
Why does a readonly root still allow writing /workspace, and why must host secrets
never be mounted even when a command was approved?
