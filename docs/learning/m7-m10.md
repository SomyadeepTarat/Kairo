# Studying Kairo M7–M10

This guide extends `docs/learning/guide.md` and `docs/learning/m3-m6.md`.
It records implementation and evidence, not a claim that you have finished studying.
Work through the source and experiments sequentially as a solo developer.

## M7: context is a view, history is evidence

A model has finite input capacity. Sending every tool result forever consumes that
capacity and increases inference work. Deleting durable history to solve this would
also destroy debugging and recovery information. Kairo keeps original context and
selects a separate view before each request.

Read `packages/core/src/kairo_core/context.py`, then the request assembly in
`packages/core/src/kairo_core/runtime.py`. `size()` measures serialized UTF-8 bytes,
including schemas. It does **not** measure model tokens, reserved output tokens, or
provider framing. `ContextPolicy` pins the first system/task pair, trims tool output,
and evicts oldest whole exchanges. `recent` keeps the suffix; `compact` may include
a bounded extract from omitted messages. Extracts lose information and cannot be
trusted as complete semantic summaries. Pinned overflow produces CONTEXT_LIMIT.

`packages/core/src/kairo_core/orchestration/spec.py` carries policy through durable
jobs. Existing checkpoints keep full history. Persisted model requests include both
the supplied `messages` and original `history_messages`; crash-gap projection in
`packages/core/src/kairo_core/orchestration/recovery.py` prefers the latter.
`context_assembled` contains a digest and run/step reference. Retrieve older steps
with the events API; full tool records remain separately inspectable. Redaction can
prevent recovery, intentionally. This is per-task history, not cross-session memory.

Alternatives and assumptions are in `docs/decisions/0011-context-budgets.md`.
There is no new dependency. Assembly is linear in retained history and serialization
size; checkpoints/history still grow with the bounded run length. Compaction is
not a guarantee that the agent remembers important facts.

Experiment: run `uv run --locked pytest tests/core/test_context.py`. Compare recent
and compact views at 600 bytes. Explain why a tool result must retain its preceding
request, why schemas count, and why an oversized pinned task fails rather than being
silently shortened. Read `tests/persistence/test_context.py` to see the difference
between actual model input and recoverable history. Predict what a model can no
longer answer after the relevant older exchange is evicted.

## M8: coordination is a durable state machine

Read `packages/core/src/kairo_core/orchestration/workflows.py`. `WorkflowSpec`
contains caller-approved job templates. `Plan` validates a dependency DAG by
repeatedly selecting vertices whose predecessors are done. If no vertex can be
added, there is a cycle or unknown dependency. This is topological progress, not
an LLM deciding whether a dependency is satisfied.

The coordinator goes PLANNING → EXECUTING → REVIEWING → COMPLETED; failures go
FAILED. Rejection returns to EXECUTING with feedback and a bounded revision count.
Runtime run states remain unchanged. Each child is a normal durable run and gets
its own attempt, lease, context and workspace. Ready independent tasks may execute
concurrently under existing worker capacity controls. The provided CLI drives one
worker sequentially, which is easier to inspect on a laptop.

A handoff records who delegated, the child run ID, time and bounded evidence. It
contains predecessor outputs and tool results. Planner/reviewer have empty tool
permissions at execution time; the coordinator can never approve model-invented
commands. It only instantiates trusted templates. `Review` requires a boolean
judgment and feedback; malformed responses fail. A reviewer is fallible and its
approval does not replace file assertions/tests.

Read `Queue.enqueue_in_transaction()` in `orchestration/queue.py`: the same SQL
transaction persists both the child job and workflow state. `WorkflowRow` in
`persistence/tables.py` and migration `migrations/versions/0004_workflows.py` persist
coordination. Holding a row lock prevents competing ticks from delegating twice.
No lock is held while a model or tool executes. Missing ticks delay progress but
do not erase state. A BLOCKED child deliberately waits for reconciliation. A failed
child ends the workflow; independently submitted siblings may still finish.

Run after `uv run --locked alembic upgrade head` with KAIRO_DATABASE_URL set:
`uv run --locked python scripts/workflow.py run examples/scripted-workflow.json`.
`submit FILE`, `advance UUID`, and `inspect UUID` permit manual tick inspection.
The same operations are exposed under `/api/v1/workflows`. These examples use
scripted role decisions and real worker/file execution, not live inference.

Study `tests/persistence/test_workflows.py`: concurrent/restarted coordinators,
DAG validation, actual files, bounded rejection, successful correction and API
inspection. Explain why retrying a tick is safe but replaying a tool may not be.
Trace which child receives which dependency output. Consider the tradeoff between
fresh revision workspaces and merging changes into existing ones; ADR 0012 records
why fresh ownership was selected. There are no automatic artifact merges.

## M9: observations, traces and evidence

Read `packages/core/src/kairo_core/observability.py`. An event says something
happened; a span describes the interval of an operation. A trace groups related
spans. `TraceRecorder` wraps the existing Recorder instead of teaching the kernel
SQL or exporters. The root is an attempt span; model and tool spans are its children.
The run UUID supplies a stable trace ID across recovery attempts. A virtual run
parent supplies identity, not an invented duration. Workflow child run IDs link
separate role traces through durable handoffs.

`runtime.py` wraps every execution, including in-memory runs. Span starts/ends and
correlation fields are added to the same persisted event payload. The SDK can export
spans, but storage is the authoritative diagnostic history. A database failure may
occur after SDK export: exported observations do not establish committed execution.
An incomplete span means no durable end was recorded. A resumed attempt does not
retroactively claim the abandoned attempt succeeded.

Two clocks have different jobs: wall time correlates systems; monotonic time measures
elapsed duration without wall-clock adjustments. Tool/model spans report measured
elapsed seconds. Total run duration includes recorded start/end and any downtime.
Structured logs omit prompts/tool data and carry run/attempt/trace identities.
Token usage is null until a provider reports it; byte counts are not tokens.

`inspect_trace()` derives counts/failures/spans from event pages. The API route is
GET `/api/v1/runs/{id}/trace`; CLI:
`uv run --locked python scripts/trace.py RUN_UUID`. For a failure, inspect run error,
failed tool code, span status/duration and the matching event sequence. Distinguish
an application failure, cancellation, and a crash with unfinished operations.

Read `tests/persistence/test_observability.py`: real SDK export into an in-memory
exporter is a test observation, not mocked OTel. Stored diagnostics use PostgreSQL.
The tests check parent IDs, error statuses, no prompt logging, cancellation and
an unfinished durable prefix. ADR 0013 explains why a local collector is optional.
Try diagnosing a missing-file run from the trace API without opening backend logs.
Then explain why a slow model span is not proof the model caused a later tool failure.

## M10: evaluation separates assertions from agent claims

Read `benchmarks/suite.json` before `packages/core/src/kairo_core/evaluation.py`.
A benchmark is a fixed task plus an independently checkable success condition and
controlled configuration. A model saying "done" is not evidence that a file is
correct. The file case compares exact contents; the coding case runs actual Python
assertions in Docker, storing the oracle command/result separately from agent tools.
The timeout and permission cases pass when the system fails/denies correctly; those
are not counted as successful autonomous tasks. Recovery-disabled interruption is
an expected scenario pass but a task completion failure.

`EvaluationConfig` selects context strategy, single/multi mode, recovery, provider,
repetitions and a fixed-case subset. Unit tests always use labelled scripted models
or labelled HTTP fixtures; live file/coding evaluations explicitly use Ollama. Other
fault scenarios remain deterministic even in an Ollama-configured suite, and each
case records its mode. Never quote scripted task completion as LLM performance.

Read `packages/core/src/kairo_core/ollama.py`. It translates Kairo's response contract
to local `/api/chat` structured JSON, then validates it back into Continue/ToolRequest/
Final. Tool execution still belongs to the registry and sandbox, not the provider.
No model-generated code is executed by the adapter. Temperature/seed/output/context
limits are fixed. HTTPX already served tests; it is now a justified runtime dependency.
Requests are loopback-only, ignore proxies, do not follow redirects, bound responses,
and never pull a model. Provider-reported counts are distinct from M7 byte budgets.
Cancellation closes client I/O; the server can take time to stop computation.

Read migration `migrations/versions/0005_evaluations.py` and `EvaluationRow` in
`persistence/tables.py`. Submission fingerprints the manifest, Python implementation,
versions, image and optional model digest. Running claims QUEUED once, commits each
case, then marks COMPLETED. COMPLETED means the evaluation finished, not that its
cases all passed. Double execution is rejected rather than silently replaying effects.
Cancellation leaves INTERRUPTED; a hard crash can leave RUNNING with partial evidence.
Start a new identity after inspection instead of pretending a benchmark can safely
resume all arbitrary effects. This differs from the agent-specific M6 resume protocol.

The interrupted scenario creates a real queued run and sandbox append, interrupts
after the persisted tool result, expires its own lease, and verifies the recovered
run did not append again. It labels the injected fault; killed-process recovery is
still covered independently in `tests/persistence/test_recovery.py`. Optional run IDs
in queue claiming/reaping isolate evaluations from other user jobs.

Single/multi file runs share the same artifact objective. Multi splits the 32-step,
120-second runtime budget across planner/executor/reviewer (4/24/4 steps, 30/60/30 s).
It receives no revision budget. Measure orchestration overhead and evidence separately;
more roles do not imply better outcomes. Fault scenarios intentionally override timing
limits. All workspaces are fresh. See ADR 0014 for exact assumptions and limitations.

### Commands to reproduce and inspect

From the repository root, with setup/env from README and Docker running:

```sh
uv sync --locked
uv run --locked alembic upgrade head
uv run --locked python scripts/evaluate.py run --repetitions 2
uv run --locked python scripts/evaluate.py run --strategy compact --repetitions 2
uv run --locked python scripts/evaluate.py run --mode multi --repetitions 2
uv run --locked python scripts/evaluate.py run --no-recovery --repetitions 2
uv run --locked python scripts/evaluate.py compare LEFT_UUID RIGHT_UUID
uv run --locked python scripts/evaluate.py inspect EVALUATION_UUID
```

For live behavior, start your existing Ollama server and select an **installed** model:

```sh
ollama list
uv run --locked python scripts/evaluate.py run --ollama qwen3:4b --cases file_task coding
```

POST `/api/v1/evaluations` queues a configuration, GET collection/detail/`results`
inspects it. `uv run --locked python scripts/evaluate.py execute EVALUATION_UUID`
executes a queued API submission. There is no background evaluator hidden in FastAPI.
No mandatory cloud services exist. These commands run from the source checkout so
`benchmarks/suite.json` is available. They can consume local CPU/RAM/storage.

### Reading results responsibly

`compare()` rejects changed source, suite, task set, seed, environment, repetition
counts or limits. It lists changed experimental factors and reports per-case paired
means and sample standard deviations. With one repetition, spread is unknown. With
two, noise still dominates many conclusions. Warm caches, thermal state and laptop
background processes are not controlled by a metadata hash. Compare outcomes first;
do not advertise timing differences as statistically proven speedups.

Start with `benchmarks/results/infrastructure-baselines.json` and the accompanying
report. Scripted context stress checks budgeting, not a model's ability to remember
lost facts. Live result snapshots remain separate and include failures; do not tune
the oracle until every answer passes. Ask: did changing the strategy improve actual
task outcome, only change overhead, or introduce another confounder? What additional
repetitions/tasks would justify a performance claim? Explain why model digest matters
when two models have the same display name.

### A cleanup failure worth studying

During final validation, a real output-limit test hung intermittently. Read `docker()`
in `execution/sandbox.py`: killing a subprocess is not enough if its output transport
is paused on a full pipe. Cancelling readers and then awaiting exit could deadlock.
Cleanup now joins cancelled readers, kills the CLI, drains bytes without retaining
them, and reaps concurrently. `test_output_limit_reaps_a_cli_with_saturated_pipes`
uses a labelled fake CLI but real OS processes/pipes to force the race. Existing
real Docker output-limit/timeout/cancellation tests validate the integrated boundary.
This is why passing a test once does not prove all asynchronous interleavings work.

## Validation history and study route

The milestone gates passed in sequence: M7 214 tests, M8 221, M9 224. The final M10
code passed 236 tests without skips, formatting/lint and strict mypy over 71 files,
with real PostgreSQL and Docker enabled. Model-dependent runs are **not** part of
that deterministic gate; inspect their separately saved results, including failures.
The source/wheel build also passed. See `docs/milestones/M7.md` through
`docs/milestones/M10.md` for failures found and fixes validated along the way.

A useful solo review order is context selection and recovery invariants, then role
state/DAG/ownership, then trace correlation, then evaluation oracles/comparability.
Follow one run UUID from submission to its events, tool records, checkpoints and
trace. Follow one workflow handoff to the next child run. Finally use evaluation
results to find an actual failed case and decide whether the failure belongs to
the infrastructure, the model protocol, or the model's task behavior. Being able
to explain that distinction is more valuable than memorizing the implementation.

### A benchmark can have bugs too

The final baseline refresh found two infrastructure errors in the interruption case
that earlier test runs did not reproduce. Inspection showed the real append and
its durable acknowledgment existed, but the job had never entered REAPING. The
benchmark used the host clock to set an expired lease; PostgreSQL used its own clock
to compare it. If the host was ahead, expiry was still in the future. An empty
`next()` lookup then became `RuntimeError: coroutine raised StopIteration` in the
async function. Production queue leases already used database time.

`test_fault_expiry_uses_database_clock` forced the evaluator's host clock one hour
forward and reproduced the failure before the fix. The injected expiry now uses
`database_now(session) - timedelta(seconds=1)`, with an explicit ownership conflict
if another worker already handled it. This is a clock-domain lesson: wall timestamps
from different machines/VMs are not interchangeable, even on one laptop.

The same failure exposed a reporting bias: infrastructure errors were excluded from
the task-completion denominator. They now count as task failures for task scenarios.
`test_infrastructure_errors_count_as_failed_tasks` verifies the denominator and the
separate error group. Stored diagnostics include safe stack file/function/line
locations without raw exception messages. Do not hide failed measurements by simply
rerunning until green; diagnose the failure and preserve pre-fix evidence separately.


Read the final [measured observations](../../benchmarks/results/README.md) with the
raw snapshots. Qwen's single file case wrote the wrong exact content; its multi
planner hit the four-call limit. The other model's continuation hit a provider
sampler HTTP 400, reproduced without invoking tools. These are different failure
classes. A working simple request does not prove every structured continuation works.
The coding oracle remains single-agent in both mode settings; the multi comparison
varies the file task, not every case in the suite. Preserve this distinction when
interpreting the tables or explaining the project in an interview.
