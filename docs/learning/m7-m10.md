# Studying Kairo M7–M10

This guide extends `docs/learning/guide.md` and `docs/learning/m3-m6.md`.
It records implementation and evidence, not a claim that you have finished studying.
Work through the source and experiments sequentially as a solo developer.

## M7: context is a view, history is evidence

A model has finite input capacity. Sending every tool result forever consumes that
capacity and increases inference work. Deleting durable history to solve this would
also destroy debugging and recovery information. Kairo keeps original context and
selects a separate view before each request.

Read `packages/core/src/kairo_core/context.py`, then the request assembly in
`packages/core/src/kairo_core/runtime.py`. `size()` measures serialized UTF-8 bytes,
including schemas. It does **not** measure model tokens, reserved output tokens, or
provider framing. `ContextPolicy` pins the first system/task pair, trims tool output,
and evicts oldest whole exchanges. `recent` keeps the suffix; `compact` may include
a bounded extract from omitted messages. Extracts lose information and cannot be
trusted as complete semantic summaries. Pinned overflow produces CONTEXT_LIMIT.

`packages/core/src/kairo_core/orchestration/spec.py` carries policy through durable
jobs. Existing checkpoints keep full history. Persisted model requests include both
the supplied `messages` and original `history_messages`; crash-gap projection in
`packages/core/src/kairo_core/orchestration/recovery.py` prefers the latter.
`context_assembled` contains a digest and run/step reference. Retrieve older steps
with the events API; full tool records remain separately inspectable. Redaction can
prevent recovery, intentionally. This is per-task history, not cross-session memory.

Alternatives and assumptions are in `docs/decisions/0011-context-budgets.md`.
There is no new dependency. Assembly is linear in retained history and serialization
size; checkpoints/history still grow with the bounded run length. Compaction is
not a guarantee that the agent remembers important facts.

Experiment: run `uv run --locked pytest tests/core/test_context.py`. Compare recent
and compact views at 600 bytes. Explain why a tool result must retain its preceding
request, why schemas count, and why an oversized pinned task fails rather than being
silently shortened. Read `tests/persistence/test_context.py` to see the difference
between actual model input and recoverable history. Predict what a model can no
longer answer after the relevant older exchange is evicted.

## M8: coordination is a durable state machine

Read `packages/core/src/kairo_core/orchestration/workflows.py`. `WorkflowSpec`
contains caller-approved job templates. `Plan` validates a dependency DAG by
repeatedly selecting vertices whose predecessors are done. If no vertex can be
added, there is a cycle or unknown dependency. This is topological progress, not
an LLM deciding whether a dependency is satisfied.

The coordinator goes PLANNING → EXECUTING → REVIEWING → COMPLETED; failures go
FAILED. Rejection returns to EXECUTING with feedback and a bounded revision count.
Runtime run states remain unchanged. Each child is a normal durable run and gets
its own attempt, lease, context and workspace. Ready independent tasks may execute
concurrently under existing worker capacity controls. The provided CLI drives one
worker sequentially, which is easier to inspect on a laptop.

A handoff records who delegated, the child run ID, time and bounded evidence. It
contains predecessor outputs and tool results. Planner/reviewer have empty tool
permissions at execution time; the coordinator can never approve model-invented
commands. It only instantiates trusted templates. `Review` requires a boolean
judgment and feedback; malformed responses fail. A reviewer is fallible and its
approval does not replace file assertions/tests.

Read `Queue.enqueue_in_transaction()` in `orchestration/queue.py`: the same SQL
transaction persists both the child job and workflow state. `WorkflowRow` in
`persistence/tables.py` and migration `migrations/versions/0004_workflows.py` persist
coordination. Holding a row lock prevents competing ticks from delegating twice.
No lock is held while a model or tool executes. Missing ticks delay progress but
do not erase state. A BLOCKED child deliberately waits for reconciliation. A failed
child ends the workflow; independently submitted siblings may still finish.

Run after `uv run --locked alembic upgrade head` with KAIRO_DATABASE_URL set:
`uv run --locked python scripts/workflow.py run examples/scripted-workflow.json`.
`submit FILE`, `advance UUID`, and `inspect UUID` permit manual tick inspection.
The same operations are exposed under `/api/v1/workflows`. These examples use
scripted role decisions and real worker/file execution, not live inference.

Study `tests/persistence/test_workflows.py`: concurrent/restarted coordinators,
DAG validation, actual files, bounded rejection, successful correction and API
inspection. Explain why retrying a tick is safe but replaying a tool may not be.
Trace which child receives which dependency output. Consider the tradeoff between
fresh revision workspaces and merging changes into existing ones; ADR 0012 records
why fresh ownership was selected. There are no automatic artifact merges.

## M9: observations, traces and evidence

Read `packages/core/src/kairo_core/observability.py`. An event says something
happened; a span describes the interval of an operation. A trace groups related
spans. `TraceRecorder` wraps the existing Recorder instead of teaching the kernel
SQL or exporters. The root is an attempt span; model and tool spans are its children.
The run UUID supplies a stable trace ID across recovery attempts. A virtual run
parent supplies identity, not an invented duration. Workflow child run IDs link
separate role traces through durable handoffs.

`runtime.py` wraps every execution, including in-memory runs. Span starts/ends and
correlation fields are added to the same persisted event payload. The SDK can export
spans, but storage is the authoritative diagnostic history. A database failure may
occur after SDK export: exported observations do not establish committed execution.
An incomplete span means no durable end was recorded. A resumed attempt does not
retroactively claim the abandoned attempt succeeded.

Two clocks have different jobs: wall time correlates systems; monotonic time measures
elapsed duration without wall-clock adjustments. Tool/model spans report measured
elapsed seconds. Total run duration includes recorded start/end and any downtime.
Structured logs omit prompts/tool data and carry run/attempt/trace identities.
Token usage is null until a provider reports it; byte counts are not tokens.

`inspect_trace()` derives counts/failures/spans from event pages. The API route is
GET `/api/v1/runs/{id}/trace`; CLI:
`uv run --locked python scripts/trace.py RUN_UUID`. For a failure, inspect run error,
failed tool code, span status/duration and the matching event sequence. Distinguish
an application failure, cancellation, and a crash with unfinished operations.

Read `tests/persistence/test_observability.py`: real SDK export into an in-memory
exporter is a test observation, not mocked OTel. Stored diagnostics use PostgreSQL.
The tests check parent IDs, error statuses, no prompt logging, cancellation and
an unfinished durable prefix. ADR 0013 explains why a local collector is optional.
Try diagnosing a missing-file run from the trace API without opening backend logs.
Then explain why a slow model span is not proof the model caused a later tool failure.
