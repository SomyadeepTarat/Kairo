## Concepts before code

A module groups responsibilities. A contract describes valid inputs, outputs,
failures and invariants. Without contracts, two separately reasonable components
can disagree about who owns cancellation or persistence. Types check part of a
contract; tests and review check behavior. Contracts can evolve together in this
monorepo until a public compatibility commitment is warranted.

A state machine is a graph of allowed lifecycle changes. It rules out impossible
history (for example COMPLETED becoming RUNNING), but does not by itself stop two
workers or persist anything. Later transactions and ownership checks supply those
properties. Keeping these guarantees separate prevents false confidence.

Dependency inversion keeps business rules independent of transport and storage.
The runtime asks a model port for structured output; an Ollama adapter implements
that request. Tests replace the adapter intentionally. A deterministic test model
proves runtime behavior, not real model competence.

Async functions allow cooperative I/O overlap. They do not make blocking subprocess
calls nonblocking or provide CPU parallelism. Cancellation must reach active work
and cleanup, and time budgets must remain bounded even when dependencies fail.

A database transaction commits related database changes together. It cannot roll
back a shell command. Idempotency means repeating an operation has the same effect;
most arbitrary commands lack that property. Recovery must distinguish known failure
from unknown completion. These are design constraints now, implementation later.

A lockfile fixes dependency resolution, not all aspects of an environment. The
interpreter, platform and installed system services still matter. Static analysis,
unit tests, service integration tests and model evaluations answer different
questions; one green check cannot stand in for all of them.

## Explain in your own words

1. Trace a task from submission through a model request, approved tool call and
   recorded result. Who may change status? Who may authorize execution?
2. Why does an HTTP cancellation response not prove that a command stopped?
3. What happens if a command succeeds and the worker dies before saving its result?
4. Why can a mocked successful model response not establish Ollama compatibility?
5. Why not build all the PRD directories or introduce Redis now?
6. Which failures can M0 detect? Which require an actual running system later?

For each future component, record: why it exists; behavior without it; alternatives;
assumptions; failure/detection/recovery; correctness tests; performance consequences.

## M0 retrospective

The repository began with a title-only README and untracked PRD. Tool CLIs existed,
but services were stopped and pytest was absent. This illustrates the difference
between installed software and a validated development environment. No throughput,
model quality or recovery measurements exist yet. As the sole developer, write your own answers and identify any contract you cannot
explain before closing M0. Use Codex to challenge your reasoning, but retain
responsibility for understanding and approving the design.
