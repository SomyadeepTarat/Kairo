## Key concepts

Calling an async function produces a coroutine; awaiting it drives its execution.
Creating a Task schedules it to run concurrently with other cooperative tasks.
The event loop can notice cancellation while a model awaits I/O. A blocking call
inside an async function still blocks the loop; async is not automatic isolation.

A timeout asks cooperative work to stop. Task.cancel() injects CancelledError at an
await point; a finally block releases resources. Cancelling without awaiting the
task can leave cleanup pending. `_request_model` therefore cancels and joins both
the request and cancellation waiter before returning. This also makes failures
visible instead of leaving unobserved background exceptions.

The per-step budget prevents one request from waiting forever. The absolute run
deadline prevents many individually acceptable requests from exceeding the total
budget. Wall clocks can jump; monotonic time measures elapsed durations. A response
returned after the budget is rejected even if the timeout callback was delayed.
Hard enforcement against blocking/noncooperative code is not provided by asyncio.

The state machine says which lifecycle changes are legal. A Continue response adds
a message while status remains RUNNING; a new model step is not a self-transition.
A Final response permits COMPLETED. A tool request is data, not permission: M1
returns FAILED with UNSUPPORTED_TOOL rather than pretending to execute it.

Frozen records make a returned history stable during normal use. Each request
contains an immutable message tuple, so later context additions cannot rewrite an
earlier request. The scripted adapter indexes by step; running the same task,
configuration and script reproduces requests, responses and transitions. UUIDs
intentionally differ. This proves infrastructure behavior, not model intelligence.

## Component reasoning

| Component | Without it / failure | Detection and response | Cost |
| --- | --- | --- | --- |
| Lifecycle policy | Invalid histories | All-pairs edge tests; reject invalid transitions | Constant-size graph |
| AgentConfig | Invalid/unbounded step or time limits | Constructor rejects invalid values, including NaN/infinity | Constant validation work |
| Model port and script | Provider coupling; nondeterministic infrastructure tests | Structured-response checks; script exhaustion becomes failure | No local inference cost |
| Execution loop | No coordinated multi-step work | Terminal outcome with request/failure records; no automatic retry | One request at a time per run |
| Cancellation race | Cannot interrupt awaited model work | Controlled blocking models verify cleanup and no named child-task leaks | Two child tasks per invocation |
| In-memory history | Cannot inspect what was supplied | Compare exact request/response records | History grows with step count and text sizes |

Alternatives and assumptions are recorded in
`docs/decisions/0005-single-agent-kernel.md`. Recovery after process failure does
not exist; rerunning creates a new run. Once tools can have side effects, rerunning
will need a separate safety analysis rather than a blanket retry policy.
