## Problem, design and alternatives

Build the smallest real loop that can receive structured model responses and stop
predictably. Keep external services out so failures can be reproduced. Use an async
Protocol, frozen dataclasses, private per-run state, monotonic budgets and explicit
cancellation. See `docs/decisions/0005-single-agent-kernel.md` for alternatives and
limits; `docs/learning/m1.md` explains the concepts before the source walkthrough.

No tool registry, filesystem tools, shell execution, HTTP adapter, database, durable
queue, approval UI, pause/resume implementation or checkpointing is included.

## Implemented contracts

- `run_agent(task, model, config=None, *, cancellation=None)` is async and always
  creates a new run/attempt. Nonempty task and valid configuration are caller
  obligations. Invalid task/config construction raises ValueError.
- `Model.generate(ModelRequest)` returns Continue, Final or ToolRequest. Request
  contains a one-based step number and immutable system/user/assistant messages.
  Continue text is appended for the next call; Final ends the run; ToolRequest fails.
- Defaults: 16 calls, 30-second per-call budget, 120-second total budget. Calls are
  sequential within a run. A final response on the last allowed call succeeds.
- Result includes UUID identities, task/config, terminal status, output or failure,
  request/response records and validated lifecycle changes. Records are in memory
  only. Failed attempted calls count toward the recorded step count.
- Failure codes: STEP_LIMIT, STEP_TIMEOUT, RUN_DEADLINE, MODEL_ERROR,
  INVALID_RESPONSE and UNSUPPORTED_TOOL. No automatic retries.
- Event cancellation returns CANCELLED after cleanup. Caller Task.cancel()
  propagates CancelledError after cleanup. Simultaneous event cancellation/final
  response chooses cancellation. Adapters must yield and honor cancellation.

## Retrospective and limitations

The kernel needs no runtime dependency or running service. Immutable request
snapshots and stateless scripted output lookup keep reproductions understandable.
Lifecycle policy alone provides neither durable state nor worker ownership.
Cancellation is cooperative, memory history has no byte/token cap, and the script
is not inference. Developer understanding remains unverified. Stop at M1; M2 tool
execution is a separate milestone and must be requested explicitly.
