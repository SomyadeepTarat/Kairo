## Testing strategy

M0 tests concern engineering utilities only. Missing Git/uv or an incompatible
Python minor must fail readiness; missing future service CLIs must not fail it.
Tests supply controlled tool discovery, so they run independently of host software.
Ruff enforces format/lint; mypy checks typed utility contracts; pytest checks behavior.
The command runner stops at the first failing command and returns its failure code.

Later milestones add actual component tests, not now: pure state/limit tests in M1;
tool schema/error tests in M2; real PostgreSQL transaction/restart tests in M3;
container/security tests in M4; races in M5; crash injection in M6. Use pytest-asyncio
when async behavior exists, HTTPX when HTTP exists, Playwright when UI exists.
Keep deterministic infrastructure tests separate from live-model evaluations.
Do not use SQLite as evidence of PostgreSQL locking correctness.

Manual M0 validation: run doctor on each machine, inspect its optional classification,
run the shared check command, and trace the lifecycle examples verbally. No
end-to-end product test is possible because no runtime exists. No performance
claims are made. Optional services being stopped is not an M0 failure.
